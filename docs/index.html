Phase 01

Design & Network

Before touching a single VM I drew the whole network, then built it: four machines on one NAT network with static addressing, so the lab behaves like a real corporate LAN.

01

Started with a network diagram

I planned the Network Structure Framework on paper first — every host, its IP, and how traffic flows through the router and switch. Diagramming first is a habit: it forces me to understand the environment and how I'd secure it before I build it.

02

Verified every installer before trusting it

I checked the SHA-256 hash of the VirtualBox download against the published value, confirming the file was the genuine, untampered installer before I ran it.

03

Set up the four VMs on one network

I provisioned all four machines in VirtualBox and switched each one to the same NAT Network so they can talk to each other under one structure — and so I can snapshot and roll back freely while testing.

04

Created the NAT network

I built a NAT network named AD Project on 192.168.10.0/24, so every server sits on the same subnet exactly like the diagram.

05

Gave the Splunk server a static IP with Netplan

On the Ubuntu box I edited the 00-installer-config.yaml file in the Netplan folder to set a static IP, applied it, and confirmed with ip a that the address was fixed and the internet was reachable (Google pinging).

06

Set up a shared folder for the server

I created the sukhwinder05 user and a share directory, then mounted my shared folder to it so I could move installation files onto the server cleanly. The mount showing green means it attached successfully.

Phase 02

Splunk & Sysmon

I built the monitoring pipeline: Splunk as the SIEM on Ubuntu, and a Universal Forwarder plus Sysmon on every Windows host, shipping rich endpoint telemetry back to the indexer on port 9997.

01

Installed Splunk on the Ubuntu server

I installed Splunk Enterprise under /opt/splunk on the Ubuntu box — this is the SIEM that ingests and indexes everything the lab generates.

02

Set the Windows client to a static IP

I changed the Windows 10 client's address to a static IP so it wouldn't collide with anything and would stay predictable for forwarding and, later, the attack.

03

Installed Sysmon on the client

I installed Sysmon on the Windows 10 machine for detailed endpoint logging — process creation, network connections, and more — the raw material good detections are built from. I also prepared the local inputs.conf to tell the forwarder what to collect.

04

Pointed the Universal Forwarder at the index

I installed the Splunk Universal Forwarder on the client and added the endpoint to the index that Splunk ingests, so the Windows 10 logs flow into the SIEM.

05

Confirmed data arriving on port 9997

Back in Splunk I verified the indexes were receiving data on port 9997 — the dedicated receiving port — proving the forwarding pipeline was live end to end.

06

Repeated it on the Windows Server

I did the same on the Windows Server 2022 domain controller — set it to 192.168.10.7 and installed Sysmon — so the DC's activity is monitored too, not just the client.

07

Tuned inputs.conf — the right way

I added the Universal Forwarder on the server and configured a local copy of inputs.conf for both machines. I deliberately avoided editing the inputs.conf in the default folder, because changing defaults can break the app — a local override is the safe, supportable approach.

08

Fixed the forwarder's permissions, and verified it's running

The forwarder service ran as the low-privilege NT account, which couldn't read every log I needed — so I changed the service logon identity to collect the full event set. Then I confirmed Sysmon and the forwarder were both running on both machines.

Phase 03 · ★ Core IT skill

Active Directory

On the Windows Server 2022 box I stood up the domain the way a real company runs it: promote the controller, organize people into OUs, create and manage users, point DNS at the domain, and join the client.

If Active Directory is on your job description, start here.Creating accounts, managing groups, DNS, and domain joins — the core admin tasks you're hiring for, done hands-on in the steps below.
01

Set a static IP for the AD server

I gave the Windows Server 2022 machine a static address and confirmed it could reach both Google and the Splunk server, so the future domain controller had reliable connectivity.

02

Installed AD Domain Services

I installed Active Directory Domain Services along with role-based access control services — the roles that turn a plain server into a domain controller.

03

Promoted it to a domain controller

I created the root domain (a .local domain) and promoted the server to a domain controller. Logging in as the domain's admin confirmed the promotion succeeded — now I could start creating users and managing the domain.

04

Built Organizational Units

I created Organizational Units to organize the company into departments — IT, HR, Employees, and so on — the structure that makes a directory manageable and lets policy target the right people.

05

Created users in the right OUs

I created domain users and placed them in the correct departments — for example a new user, Jenny Smith, added to IT, and another user added to HR.

06

Pointed DNS at the domain

I changed DNS from 8.8.8.8 to my Active Directory domain service, so domain name resolution runs through the controller — a requirement for machines to find and join the domain.

07

Joined the client to the domain

With DNS pointed correctly, the client was allowed to join the domain, and every user I created in AD could then sign in on it. The ipconfig on the client confirms its static IP and that DNS points at the DC.

Phase 04

Validation & Atomic Red

With the domain and monitoring in place, I needed to prove the logging actually worked. So I ran a controlled attack from Kali, confirmed the telemetry caught it in Splunk, and then used Atomic Red Team to find exactly where I was still blind.

01

Placed Kali on the network per the diagram

I set the Kali machine's IP to match my diagram and confirmed it could ping the network, then made a working directory to keep the files I'd use.

02

Prepared the password wordlist and enabled RDP

I copied a password wordlist into the project directory and unzipped it, then enabled Remote Desktop for specific users on the Windows target — the service the brute force would hit.

03

Ran the brute force with Crowbar

From Kali I used Crowbar over RDP against the Windows target — account tsmith (Terry Smith) at 192.168.10.100 — using the wordlist I'd saved. Crowbar worked through the list and returned RDP-SUCCESS, meaning a valid credential was found.

kali@kali: ~/Desktop/ad-project
└─$ crowbar -b rdp -u tsmith -C passwords.txt -s 192.168.10.100/32
Trying 192.168.10.100:3389
RDP-SUCCESS : 192.168.10.100:3389 - tsmith:P@ssw0rd1!
04

Found the attack in Splunk — 20× Event 4625

Back on the Splunk server I checked what telemetry the attack generated. There were twenty Event 4625 records — and when I looked up that code, it means failed logon. My monitoring pipeline had captured the attack.

4625Failed logon
4624Successful logon
4776Credential validation
05

Recognized the brute-force signature

Looking closer, all of those failures happened at the same time — a burst of failed logons in one instant is a clear indicator of an automated brute-force attack, not a user mistyping a password.

06

Traced the successful logon back to Kali

Searching for Event 4624 showed a single successful logon right after the 20 failures — the attack worked. And the successful event told me where it came from: my Kali machine and the exact IP I attacked from. That's a full compromise reconstructed from logs.

07

Installed Atomic Red Team

To test more techniques, I installed Atomic Red Team. First I added a scoped Microsoft Defender exclusion so the security tooling wouldn't quarantine the test files mid-run, then installed it with its dependencies. Atomic Red provides "atomics" — small tests, each tied to a technique ID that maps to MITRE ATT&CK.

T1110Brute Force · RDP T1136.001Create Account · Local T1059.001PowerShell T1059.003Windows Command Shell
08

Tested Create Account (T1136.001) — and found a visibility gap

I ran the T1136.001 test, which creates a local account (NewLocalUser), then went back to Splunk to see if it showed up. Nothing came up — and that was the valuable result.

The gap was the finding

If nothing appears, it means I'm blind to that activity. If an attacker compromised the system and created a local account under those settings, I wouldn't detect it. That's not a failure — it's a precise map of where to build the next detection. This is exactly what Atomic Red Team is for: surfacing visibility gaps.

09

PowerShell technique (T1059) — captured and ready for alerting

Next I ran the command and scripting / PowerShell technique. Defender even caught some of it (which is why the earlier exclusion mattered), and in Splunk I could see the exact command that Atomic Red had run. That means I can build alerts on this activity going forward — Atomic Red surfaces it, and Splunk makes it detectable.

Why this phase mattered

The point wasn't to "hack" my own lab — it was to validate the monitoring and find my blind spots. I confirmed the pipeline catches a real attack, learned exactly which techniques I couldn't yet see, and set up the account hardening that comes next.

Phase 05

Hardening & Administration

After seeing what the attack and Atomic Red revealed, I went back into Active Directory and tightened it up — managing access through groups, restricting when people can log in, and ending access automatically when it should end.

01

Managed access with security groups

I added users to group objects so many people share the same permissions at once — instead of manually assigning permissions to thousands of accounts one by one. Group-based access is the only way permissions stay manageable and auditable at scale.

02

Populated a realistic work environment

I created simulated data and users across the departments so the domain behaves like a real, running company — the realistic backdrop needed to test policy and troubleshooting properly.

03

Restricted logon hours

I set time-based access control on accounts so employees can't log in during a set window. That protects maintenance work — backups and software updates run cleanly when no one is logged in and changing data.

04

Set accounts to expire automatically

I configured account expiration so contractor accounts end on their due date. Once a contract is up, the account expires on its own — the person can't reach company information afterward, with no manual cleanup to forget.

Phase 06 · ★ The day job

Troubleshooting

Running a domain means solving the problems employees actually hit. I worked through the most common ones in my simulated environment, step by step — including what to do when the quick fix doesn't hold.

This is the day-to-day work you're hiring for.Password resets, unlocks, access requests, and machines that fall off the domain — each one worked below as symptom → diagnosis → fix.
01

User locked out — reset and unlock

A common issue: a user is locked out and can't log in. I confirmed the account was locked in AD, then reset the password and unlocked the account. For a one-off, that's the whole fix.

02

Recurring lockout — trace the real source

But what if the account locks again every 20 minutes, even after resetting the password and unlocking it? A recurring lockout isn't a password problem. I used Event Viewer to review the security logs — who was logging in and when — and pinpointed the exact computer generating the bad logons (usually a stale cached credential, a mapped drive, or a service still using the old password). Fix the source, and the lockout stops.

03

Account expired

Another case: a valid user suddenly can't log in, with no lockout. The cause is often an expired account — the expiration date I set in hardening has passed. If the person is staying, I extend or remove the expiration; if not, the cutoff worked exactly as intended.

04

Can't access a resource — fix it through the group

A new HR hire, Berry, needs to create files in the HR share but gets access denied. I went to AD and checked her Member Of tab — empty. I compared her to a working HR peer, who was in the $HR-Staff group, and confirmed on the HR folder's NTFS security that $HR-Staff has full control. Berry was never added. Adding her to the group — not setting one-off permissions — fixed it the right way.

05

Broken workstation trust relationship

The toughest of the four: a machine shows "The security database on the server does not have a computer account for this workstation trust relationship." This happens when a computer has been off the domain too long and its secure channel breaks. The fix takes more steps:

① Sign in with the local admin account (not the domain — add .\ so it signs into the local account). ② In the PC's properties, drop it into a workgroup to un-domain it, and reboot. ③ In AD, delete the stale computer object — if you keep the same computer name, the old object must be deleted first or the rejoin conflicts. ④ Rejoin the domain and log back in.

The detail that saves an afternoon

Knowing you must delete the old computer object in AD before rejoining with the same name is the difference between a five-minute fix and hours of conflicts.
